## 1. Role & context

You are working on a **containerized credit scoring & fraud detection platform** (FastAPI + MLflow + Airflow/Spark + PostgreSQL + MinIO) that turns a customer's national ID into a credit decision (score, risk band, limit, interest rate). It's currently a **working reference implementation trained on synthetic data**, and the goal is to bring it up to a standard that a bank's **model risk management / credit risk function** would accept for real lending decisions.

Treat this as **regulated financial software**, not a generic ML project. That means: every change needs to be explainable to a non-technical credit committee, every model artifact needs to be versioned and reproducible, and nothing that affects a lending decision should ship without a documented rationale.

Read these existing docs before making changes — they are the ground truth for how the system currently works, don't assume or invent behavior:
- `index.md`, `architecture.md`, `credit-scoring.md`, `scoring-engine-algorithm.md`
- `training-and-registry.md`, `ml-pipeline.md`, `runtime.md`, `deployment.md`
- `data-model.md`, `api-reference.md`, `authentication.md`, `fraud-detection.md`
- `model-risk-and-weaknesses.md` if present

## 2. Known weaknesses (do not treat these as unknowns — they're already diagnosed)

1. **Circular training target.** `payment_history_score` is generated by a hand-written formula (DTI/utilization/late-payment penalties + income/employment bonuses + noise) in `generate_dummy_data.py`, not observed repayment behavior. The GBT/RF models are learning to approximate that formula, not real default risk.
2. **No reject-inference / sample-bias handling.** No tracking of declined applicants for future model training.
3. **No monitoring or backtesting pipeline.** Training DAGs exist; nothing validates ongoing prediction quality (no PSI/CSI, no Gini/KS trend, no calibration backtest). No automated test suite in the repo.
4. **No transparent/explainable benchmark model.** All three credit models are tree ensembles (GBT/RF); there's no logistic regression / WOE scorecard acting as an auditable benchmark.
5. **Two inconsistent trainers.** `train_models_pandas.py` (deployed) correctly excludes the score target from features; the Spark equivalent `train_models.py` does not — both register to the same MLflow model names.
6. **No calibration to a stable score/PD scale.** `risk_probability` and `interest_rate` are `random.uniform` draws within a score tier, not derived from a calibrated probability.
7. **No override/fairness monitoring.** Guard-rail triggers (DTI hard-reject, over-leverage cap, subsistence-income cap) aren't logged as structured, queryable override events.
8. **Minor:** `USD_TO_TZS_RATE = 1` no-op currency conversion; redundant score↔risk↔limit outputs that are mostly overridden by policy anyway.

## 3. Non-negotiable constraints while making changes

- **Never let WOE/bucket boundaries be recomputed on scoring/production data.** If you build a WOE pipeline, boundaries and WOE values must be fit once on the training/development sample, frozen, versioned (e.g. JSON artifact keyed by model version), and applied identically at inference time.
- **Never let a model see its own target or a proxy for it in training features.** Preserve and extend the existing leakage-exclusion discipline (`payment_history_score`, `risk_category_target`, `is_approved`, `is_fraud`, `is_high_risk`, IDs) to any new derived features you add.
- **Every model artifact must be reproducible from a versioned config** — no silent/manual retraining steps that can't be traced back to a specific data snapshot + feature definition + hyperparameter set.
- **Every override / guard-rail trigger must be logged**, not just enforced — decision, pre-override score, post-override decision, reason, actor (system/human), timestamp.
- **Don't delete the existing rule-based guard rails or weaken them** — you're adding rigor, not removing safety controls.
- **Keep the two model families independent and swappable** (score/risk/limit as separate MLflow-registered models) — don't collapse them into one multi-output model.
- **Flag, don't silently fix, anything touching the synthetic-target problem** (#1 above) if fixing it requires real data you don't have — implement the plumbing (target definition abstraction, feature flags) so it's a one-line change when real repayment data exists, but don't fabricate fake "real" labels to make the problem look solved.
- **Write or update docs alongside code.** Any change to feature definitions, model targets, or the rules engine must be reflected in the corresponding `.md` file in the same PR/commit — undocumented model behavior is itself a finding in a bank audit.

## 4. Work phases — do these in order, confirm completion of each before starting the next

### Phase 1 — Governance & documentation hygiene (cheap, do first)
- [ ] Add an explicit, prominent disclosure in `scoring-engine-algorithm.md` (or a new `model-limitations.md`) stating the target is synthetic/formula-derived, not empirical, and what that implies for current Gini/F1 metrics.
- [ ] Fix `train_models.py` (Spark trainer) to exclude `payment_history_score` from its feature set, matching `train_models_pandas.py`. Add a test that fails if any target/leakage column ever appears in either trainer's feature list.
- [ ] Add a `model_version` / `training_run_id` field that's threaded from training → MLflow registration → served prediction → decision log, so any live decision can be traced back to the exact model artifact and data snapshot that produced it.

### Phase 2 — Monitoring & backtesting infrastructure (build before you need it)
- [ ] Add a scheduled Airflow DAG that computes **Population Stability Index (PSI)** comparing current scoring-population feature/score distributions against the training-sample baseline. Alert if PSI > 0.25.
- [ ] Add a job computing **Gini/AUC and KS-statistic** on a rolling window of scored cases (once outcome labels exist), segmented by product/region where volume allows.
- [ ] Set up a minimal automated test suite: unit tests for the feature pipeline (`fetch_features`), the business-rules engine (`apply_business_rules`), and a regression test that pins expected output for a fixed synthetic input (catches silent behavior drift across refactors).
- [ ] Add structured logging for every guard-rail trigger — write to a queryable `overrides` table (or equivalent) with: applicant/loan id, rule name, pre-override model output, post-override decision, timestamp.

### Phase 3 — Explainable benchmark model (governance artifact)
- [ ] Build a WOE/Information-Value feature pipeline: fine-classed univariate analysis, coarse classing (min bucket size ~100, min goods/bads ~25 each), WOE transform — as a versioned, frozen artifact (see constraints above).
- [ ] Fit a logistic regression scorecard on the WOE-transformed features as a benchmark model, registered in MLflow alongside the GBT model under a clearly distinct name (e.g. `CreditScoreScorecard`).
- [ ] Report Gini/KS for both the scorecard and the GBT model side by side at every training run — this becomes the standard "is the opaque model earning its complexity" check.
- [ ] Generate a delta-score-based reason-code function from the scorecard (points lost vs. best attribute per variable) as a second, fully transparent explainability path alongside the existing SHAP `/explain` endpoint.

### Phase 4 — Calibration
- [ ] Pick and document a fixed odds-to-score convention (e.g. good:bad odds 1:1 at score 500, doubling every 20 points) and apply it consistently to both the logistic scorecard and a calibrated version of the GBT output (Platt scaling or isotonic regression, fit on a held-out calibration slice, not training data).
- [ ] Replace the `random.uniform` draws for `risk_probability` and `interest_rate` with values derived from the calibrated PD.
- [ ] Fix the `USD_TO_TZS_RATE` no-op — either implement real conversion or relabel outputs accurately until it's implemented.

### Phase 5 — Reject-inference plumbing (data model change, ahead of real-data migration)
- [ ] Add a `decision_population` field (accepted / declined / override) to the data model so declined applicants' features are captured even though they're not currently used in training.
- [ ] Document (don't yet implement, unless real decline data exists) the intended reject-inference approach for when real labels arrive: prefer data methods (reject acceptance sample or bureau surrogate data) over inference methods (augmentation/extrapolation), per the documented rationale in the project's model guidelines.

### Phase 6 — Real-data migration readiness (only when repayment outcome data exists)
- [ ] Build the target-definition abstraction so `payment_history_score`'s training target can be swapped from the synthetic formula to an empirical good/bad label (e.g. 90+ DPD within a defined performance window) via config, without touching the rest of the pipeline.
- [ ] Once swapped, re-run Phase 2's PSI/Gini backtests to confirm the model trained on real data is actually predictive before promoting to `Production` in MLflow.

## 5. Definition of done per change
